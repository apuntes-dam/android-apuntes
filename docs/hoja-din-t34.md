<h3 class="hd-tema">Tema 3 · Documentos de descripción <small>(20 preguntas)</small></h3>
<div class="hd-lista">
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">1</span>Hasta hace poco, ¿qué dos lenguajes para una pantalla Android y qué papel tenía el XML?</div><div class="hd-r">XML para el diseño (los layouts) y Java o Kotlin para la lógica. El XML era el «documento de descripción»: qué botones, textos y campos tiene la pantalla y dónde van.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">2</span>¿Qué cambia con Compose y por qué sigue importando el XML?</div><div class="hd-r">Compose describe la interfaz directamente en Kotlin declarativo, sin documento intermedio. El XML sigue importando: intercambio de datos (RSS, facturas, mapas GML), otras plataformas (XHTML, SVG, XUL) y los layouts heredados.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">3</span>Idea central: equivalencias entre describir y programar una interfaz</div><div class="hd-r">Una interfaz se describe (en un documento) o se programa (en código). Mismas piezas: etiquetas ↔ composables, atributos ↔ parámetros, eventos ↔ lambdas.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">4</span>XML: ¿qué es?</div><div class="hd-r">eXtensible Markup Language («lenguaje de marcas extensible»). Es un metalenguaje: no describe nada por sí mismo, pero permite definir lenguajes que sí lo hacen.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">5</span>XHTML</div><div class="hd-r">(eXtensible HyperText Markup Language) Lenguaje de marcas de las webs. Exige documentos bien formados: toda etiqueta cerrada, atributos entrecomillados y un único nodo raíz. En Compose se incrusta con un <code>WebView</code>.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">6</span>GML</div><div class="hd-r">Geography Markup Language. Describe datos geográficos (puntos, rutas, zonas) como documentos XML. La ficha de un mirador es un documento GML y la pantalla que lo muestra se genera a partir de él.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">7</span>MathML</div><div class="hd-r">(Mathematical Markup Language) Describe fórmulas matemáticas con etiquetas (<code>&lt;mfrac&gt;</code> fracción, <code>&lt;msup&gt;</code> exponente). Android no lo entiende de forma nativa: se mete en un <code>WebView</code>.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">8</span>RSS/Atom</div><div class="hd-r">(RSS: Really Simple Syndication) El XML de las noticias: un <code>&lt;channel&gt;</code> con <code>&lt;item&gt;</code>s (title, link, description). Un lector es un parser de RSS que compone una interfaz: antes <code>ListView</code> con adaptador, en Compose un bucle.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">9</span>XSLT</div><div class="hd-r">(eXtensible Stylesheet Language Transformations) XML que transforma otros XML: reglas del tipo «cada vez que veas <code>&lt;titulo&gt;</code>, saca un <code>&lt;h2&gt;</code>». Abuelo de la capa de presentación: datos → representación.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">10</span>SVG</div><div class="hd-r">(Scalable Vector Graphics) Gráficos vectoriales en XML: una lista de trazados (<code>path</code>), no un mapa de bits. Android: Vector Drawable (XML); Compose: <code>ImageVector</code> (<code>d</code> → <code>pathData</code>, <code>addPathNodes</code>).</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">11</span>Los tres conceptos de un documento XML</div><div class="hd-r">Etiquetas, atributos y valores. Documento XML = etiquetas + atributos + valores ↔ composable = función + parámetros + argumentos.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">12</span>Etiquetas</div><div class="hd-r">Una etiqueta abre un elemento y encierra contenido u otros elementos. Clásico: <code>&lt;Button android:text="Enviar" /&gt;</code>. Compose: una función llamada en el orden de pintado, <code>Button(onClick = { … }) { Text("Enviar") }</code>.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">13</span>Atributos (y ventaja de los parámetros)</div><div class="hd-r">Propiedades del elemento: en XML entre comillas dentro de la etiqueta; en Compose, parámetros con nombre (<code>textSize="14sp"</code> → <code>fontSize = 14.sp</code>; <code>layout_marginTop</code> → <code>Modifier.padding(top = 8.dp)</code>). Los parámetros admiten expresiones, no solo literales.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">14</span>Valores: dos formas y regla de oro</div><div class="hd-r">Un literal (<code>23,5</code>) o una referencia a recurso (<code>@string/temperatura</code>). Regla de oro: nada de valores mágicos en el layout. En Compose, <code>stringResource</code> y los colores del <code>MaterialTheme</code>.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">15</span>Eventos</div><div class="hd-r">Antes, conexión por nombre: <code>android:onClick="enviar"</code> buscaba un método en la actividad (acoplamiento débil; una errata no la avisaba el compilador). Ahora, una lambda directa y el estado con <code>remember</code>.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">16</span>Editores de documentos XML (compara)</div><div class="hd-r">Notepad++: texto, Windows, plugins (XML Tools). Atom: muerto en 2022 (vive en Pulsar). Dreamweaver: IDE visual web (WYSIWYG), en declive. VS Code: el estándar actual. Android Studio: la nuestra, con <code>@Preview</code>.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">17</span><code>@Preview</code></div><div class="hd-r">El generador de interfaces integrado: ejecuta un composable en el panel de diseño sin lanzar el emulador. Con <code>@PreviewParameter</code>, <code>@UiMode</code> o <code>@Configuration</code> se sacan variantes (oscuro/claro, fuentes, dispositivos).</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">18</span>Generación de código para varias plataformas</div><div class="hd-r">Antes, de un mismo XML se generaba código para Java, C++ o web. Hoy, dos lecturas: la interfaz se «genera» sola desde el código (Compose emite el árbol de dibujo) y la app va a varias plataformas con Kotlin Multiplatform (se ejecuta, no se traduce).</div></div>
<div class="hd-i hd-C" title="Menos probable"><div class="hd-q"><span class="hd-n">19</span>Caso práctico 1: logo con gráficos vectoriales</div><div class="hd-r">Estrella SVG: <code>d</code> → <code>pathData</code> con <code>addPathNodes</code> → <code>ImageVector</code> (<code>fill</code> original en <code>SolidColor</code>) → <code>Image</code> en una <code>Box</code> con degradado → probar a 40, 140 y 400 dp: al ser trazados, no pixelea.</div></div>
<div class="hd-i hd-C" title="Menos probable"><div class="hd-q"><span class="hd-n">20</span>Caso práctico 2: ficha GML/RSS editable</div><div class="hd-r">Dos <code>OutlinedTextField</code> anclados a <code>remember</code> (la edición del documento) y una <code>Card</code> que refleja el estado (la interfaz generada, que se actualiza al vuelo).</div></div>

<h3 class="hd-tema">Tema 4 · Crear componentes <small>(22 preguntas)</small></h3>
<div class="hd-lista">
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">21</span>Define componente</div><div class="hd-r">Código probado y reutilizable que se comunica con el resto por su interfaz pública: parámetros de entrada y eventos de salida. Lo que no está en ella es interno y puede cambiar sin romper a nadie.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">22</span>Programar «en componentes»</div><div class="hd-r">Ensamblar piezas ya hechas en lugar de escribirlo todo desde cero.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">23</span>Ventajas del desarrollo por componentes</div><div class="hd-r">Reutilización (se escribe una vez) · fiabilidad (ya está probado) · coste y plazo (componer en vez de escribir) · consistencia (se ve igual en toda la app) · mantenimiento (cambiar algo es tocar una línea).</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">24</span>Define componente de interfaz</div><div class="hd-r">Pieza de código que dibuja una parte de la pantalla y se comporta de forma predecible.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">25</span>Las seis cosas que se le piden</div><div class="hd-r">1 Interfaz pública clara · 2 valores por defecto sensatos · 3 sin efectos sorpresa (ni datos en sitios raros, ni ficheros, ni redes) · 4 comunicación por eventos (lambdas) · 5 aislado y portable (sin Activity) · 6 documentado y probado.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">26</span>¿Qué es un componente en Compose?</div><div class="hd-r">Una función <code>@Composable</code>. No hay clase base que heredar ni paleta donde registrarlo: el editor la entiende, la previsualiza y Layout Inspector la muestra.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">27</span>Propiedades y valor por defecto</div><div class="hd-r">Las propiedades son los parámetros de la función; el valor por defecto de una propiedad es el valor por defecto del parámetro.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">28</span>El parámetro <code>modifier</code></div><div class="hd-r"><code>modifier: Modifier = Modifier</code>, siempre el primer parámetro opcional: quien llama coloca y da tamaño al componente sin tocar su código. Se aplica al contenedor raíz.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">29</span>JavaBean: ¿qué pedía?</div><div class="hd-r">Clase pública con constructor sin argumentos, que implementa <code>Serializable</code>, con propiedades privadas accesibles por <code>getX()</code>/<code>setX()</code> y eventos por escucha.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">30</span>¿Qué queda de JavaBean?</div><div class="hd-r">La idea: datos públicos bien definidos, constructor sencillo y comportamiento predecible. La sintaxis sobra: Kotlin convierte cada propiedad en getter y setter.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">31</span>Firma de <code>BadgeEstado</code></div><div class="hd-r"><code>BadgeEstado(estado: Estado, texto = estado.etiqueta, modifier = Modifier, conPunto = true, relleno = estado.acento.copy(alpha = 0.15f))</code>. El único obligatorio es <code>estado</code>; <code>relleno</code> es el acento al 15 % de opacidad.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">32</span><code>Estado</code>: <code>etiqueta</code>, <code>acento</code> y <code>mensaje</code></div><div class="hd-r">Un <code>enum class</code> con datos: OK «Completado», AVISO «Revisa», ERROR «Fallido». <code>etiqueta</code> = texto, <code>acento</code> = color de referencia, <code>mensaje</code> = frase larga. Color y mensaje viajan dentro del estado, no repartidos por las pantallas.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">33</span><code>BadgeEstado</code> por dentro</div><div class="hd-r"><code>Row</code> con <code>testTag</code>, recorte en píldora y fondo <code>relleno</code>: un punto (<code>Box</code> circular de 10 dp) y un <code>Text</code> con <code>labelLarge</code>. No sabe en qué pantalla está ni crea estado propio. Lleva un <code>@Preview</code> con los tres estados.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">34</span>¿Por qué sin estado propio se reutiliza mejor?</div><div class="hd-r">Porque el estado lo decide quien lo usa y el componente solo dibuja lo que le cuentan. El estado interno se deja para lo interno (por ejemplo, si un menú está abierto).</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">35</span><code>SelectorMes</code> frente a <code>BadgeEstado</code></div><div class="hd-r"><code>SelectorMes</code> devuelve información a la pantalla mediante un evento: un parámetro lambda (<code>onSeleccion: (Int) -&gt; Unit</code>).</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">36</span>Caso del abono del metro</div><div class="hd-r">El componente no sabe qué es un abono: <code>SelectorMes</code> solo sabe de meses. El precio y la confirmación son de la pantalla. Así se reutiliza en una cita médica, una reserva o una matrícula.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">37</span>Herramientas para diseñar y probar</div><div class="hd-r">Material gráfico: Figma, Inkscape, Vector Asset Studio. Componente: <code>@Preview</code>, <code>@PreviewParameter</code>, tema oscuro, Layout Inspector, Compose Testing (<code>createComposeRule</code>) y lint/Detekt.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">38</span>¿Qué comprueba una prueba de un componente?</div><div class="hd-r">Que el usuario ve lo correcto, no que «el código se ejecuta». Se monta con <code>createComposeRule</code>, se busca por <code>testTag</code> o por texto y se afirma sobre lo visible.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">39</span>¿Cómo se documenta un componente?</div><div class="hd-r">KDoc en la declaración (<code>/** … */</code> con <code>@param</code>) · un <code>@Preview</code> por estado (documentación viva) · Dokka (el Javadoc de Kotlin) si se publica.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">40</span>Empaquetarlo y usarlo</div><div class="hd-r">Un módulo de librería (<code>.aar</code>: clases, recursos y manifiesto); la «paleta» es el <code>dependencies</code> de Gradle. Quien lo usa escribe <code>implementation(project(":ui"))</code>: no copia ficheros.</div></div>
<div class="hd-i hd-A" title="Muy probable"><div class="hd-q"><span class="hd-n">41</span><code>api</code> frente a <code>implementation</code></div><div class="hd-r"><code>api</code> filtra la dependencia a quien te usa; <code>implementation</code> la esconde. Un kit de interfaz usa <code>api</code> para Compose.</div></div>
<div class="hd-i hd-B" title="Probable"><div class="hd-q"><span class="hd-n">42</span>Dibujar a mano: el lienzo</div><div class="hd-r"><code>DrawScope</code>, dentro de <code>Canvas { }</code> o de <code>Modifier.drawBehind { }</code>. Es el <code>java.awt.Graphics</code> de hoy.</div></div>
